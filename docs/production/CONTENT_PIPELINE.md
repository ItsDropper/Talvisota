# Content pipeline

## Separation of concerns

- `assets/` contains source and processed media: models, textures, materials, audio, and UI assets.
- `content/` contains authored game definitions that refer to assets by stable identifiers.
- `data/schemas/` contains versioned schemas used to validate authored definitions.
- `tools/asset_pipeline/` contains game-specific orchestration and packaging commands.
- Generic model import, image decoding, CPU asset validation, mip processing, and GPU resource ownership belong to VantaEngine.

Do not use filesystem paths as persistent gameplay identifiers. Content references use stable IDs resolved through the Talvisota manifest.

## Headless content validation

`talvisota_content_validate <manifest> <content-root>` validates the manifest, path containment, provenance, dependency graph, typed PBR materials, typed world definitions, and typed mission/faction/character/equipment definitions. It does not claim to decode media.

## Engine-backed media validation

On Windows x64/MSVC, configure with `TALVISOTA_ENABLE_VANTA_ENGINE=ON`. The optional `talvisota_asset_validate` command uses VantaEngine's `ModelAssetStore`, OBJ/glTF/GLB importers, and WIC texture decoder. It validates imported geometry and materials, decodes registered texture assets, and checks that model-referenced textures remain inside the content root, resolve to manifest texture assets, and are declared as model dependencies. This path is CPU-only and does not initialize a graphics device.

The pinned VantaEngine revision supports Wavefront OBJ with multiple MTL sidecars and material/submesh assignment, glTF 2.0/GLB static meshes, WIC-supported external texture images, base64/percent-encoded glTF data-URI images, and GLB buffer-view images. Embedded image payloads remain owned by imported CPU materials; the importer does not extract mutable sidecar files. OBJ `mtllib` sidecars must be registered as `.mtl` material assets and declared as model dependencies; MTL texture maps must also be registered texture assets and declared as model dependencies. Multiple `mtllib` declarations and multiple libraries on one declaration are supported; `usemtl` is resolved into named CPU materials and submesh ranges. Embedded glTF image payloads are decoded through WIC during engine-backed validation. Texture source support follows installed WIC codecs; the Talvisota manifest accepts BMP, PNG, JPEG, and TIFF variants for this path.

## Deterministic texture processing

The `talvisota_texture_process <source> <output.ttex> <srgb|linear|normal>` command is available with the optional engine adapter. It decodes the source through VantaEngine WIC and writes a deterministic little-endian `TVTTEX01` container. `srgb` filters colour RGB in linear light; `linear` box-filters non-colour data without gamma conversion; `normal` is for tangent-space normal maps, normalizes decoded source vectors, averages unit vectors and renormalizes every mip, and filters alpha linearly. Normal maps are serialized with linear colour-space metadata. The container contains a version, dimensions, RGBA8 format, colour-space tag, mip count, and pixel bytes; it contains no timestamps, absolute paths, or host-endian metadata. The engine-backed validator reads `.ttex` files with the strict VantaEngine container reader, including dimension/mip-chain/size/trailing-byte validation.

## Typed PBR materials

Material assets use the strict, versioned `.tmat` format documented in [material-definition-v1.md](../../data/schemas/material-definition-v1.md). The parser validates finite numeric values, physically based parameter ranges, stable material identity, manifest ownership, and texture-slot references. A referenced texture must be a texture-kind asset, be present as a regular file, and be listed as a dependency of the material.

Base-colour and emissive texture RGB are sRGB; normal and ORM textures are linear. ORM channels are R=occlusion, G=roughness, B=metallic. These are authoring/import contracts; renderer consumption remains subject to the pinned engine's material API.

## Typed world definitions

World metadata uses the strict, versioned `.tworld` format documented in [world-definition-v1.md](../../data/schemas/world-definition-v1.md). Version 1 fixes the world coordinate convention to metres, right-handed, +X east, +Y up, and +Z north. Bounds must be finite and strictly ordered on every axis. Optional sea level must fall within vertical bounds. Optional `terrain_model_id` must resolve to a present model asset and be an explicit dependency of the world manifest record.

The repository includes a 64-metre Central Finland region with an OBJ/MTL terrain mesh, a 17x17 `.tregion` heightfield sampled from the same OBJ vertex grid, a snow albedo texture, and a typed snow material. The game-owned world runtime bilinearly samples elevation and surface normals from this grid; tests compare all 289 grid samples to the source mesh vertices. The same region composes eight original Norway spruce models and three snow-capped boulders through stable asset IDs, with independent authored collision volumes. The spruce source contains 13,320 positions, 13,320 cylindrical UV coordinates, and 19,992 triangles. The boulder is a deterministic four-level subdivided icosphere with multi-frequency displacement, 2,562 positions, 2,562 spherical UV coordinates, and 5,120 triangles, partitioned into rock and snow material groups. Engine-backed validation imports the models and MTL sidecars, and deterministic packaging includes and revalidates the complete content set. These Central Finland validation assets remain deliberately simple; the Sakkola environment below carries the current generated PBR material set and engine normal-map path.

The first historically grounded Karelian environment is Sakkola Kirkonkylä and the north shore of Suvanto. Its 4,096-metre terrain mesh tiles the 1024px snow PBR maps every 40 metres (UV span 102.4 on each 4,096-metre axis); a dedicated asset-contract test prevents the entire region from collapsing back to one texture repeat. Its current authored region spans 4,096x4,096 metres and uses a 177x177 heightfield at approximately 23.2727-metre spacing, matched vertex-for-vertex to the terrain OBJ grid. It contains 3,094 vegetation placements across five species (1,667 Scots pine, 140 Norway spruce, 100 additional pine, 497 silver birch, 351 aspen, and 339 alder), 32 boulder placements, 48 structure-category placements (35 exterior buildings plus 13 interior model placements), and 803 prop-category placements. The prop category includes 420 common-juniper placements, 300 winter-brush clumps, 28 fallen logs, 26 stumps, 12 fence sections, 12 reed placements, two woodpiles, a well, the frozen Suvanto surface, and the packed rural track. The forest is authored as a mixed stand with species-specific silhouettes and scale/yaw variation rather than a single repeated spruce mesh. The source reference is the National Land Survey of Finland's pre-war 1:20,000 topographic sheet 404206_SAKKOLA.tif; the current terrain elevations and shoreline are a hand-authored blockout informed by the historical setting, not a georeferenced extraction of that raster. See [Sakkola environment references](SACKKOLA_ENVIRONMENT_REFERENCE.md) for source notes and remaining historical/geospatial work.

The environment generator produces 41 separate 1024x1024 BMP maps: albedo, tangent-space normal, roughness, and ambient occlusion for ten material families (bark, pine needles, birch bark, aspen bark, alder bark, granite, snow, packed snow, ice, and reeds), plus a packed snow ORM map. `talvisota_environment_texture_gen` produces material-specific multi-scale maps from original source code and verifies periodic continuity at both UV boundaries for all ten procedural fields before writing. The generated 8-bit snow and packed-snow albedo maps are additionally checked per colour channel for a minimum standard deviation of 1.5 levels after sRGB encoding; aggregate RGB range alone is insufficient because channel-to-channel colour separation can mask a nearly constant channel. The packed-snow compression field uses independent integer U/V periods, so its anisotropic scale remains tileable. The `Talvisota.Environment.PbrMaps` CTest also verifies all 41 generated BMP files. Output is generated under `assets/textures/environment/` during the normal CMake build and before content validation/packaging. The generated BMPs are intentionally ignored by Git and recreated deterministically. This is a substantive procedural PBR first pass, not a claim that scanned or hand-painted final art has been completed.

The Scots pine and granite-boulder Blender pipelines each emit four separate deterministic GLBs. LOD0 remains required; LOD1-LOD3 are optional manifest assets so a checkout without CI-generated runtime artifacts remains content-valid. The MSVC renderer job uploads and downloads the complete chains and verifies all eight files. At runtime, SakkolaSceneBuilder imports the contiguous available levels once, maps submeshes by stable material-slot index, reuses the LOD0 material index whenever the imported PBR material is identical, and keeps exactly one scene instance per material-bound placement. The culler selects LOD from the authored projected-screen-coverage hints (Scots pine: 0.75/0.40/0.18/0.0; boulder: 0.30/0.10/0.025/0.0), using the model's LOD0 bounds and active camera FOV; missing optional levels extend the final available level to zero coverage. A present but malformed level fails scene construction. Each LOD-enabled render instance carries a validated species group (Scots pine or granite boulder), so capture diagnostics can separate the two chains rather than infer tree selection from aggregate counts. The first generated CI artifacts (run 42882137917) contain 438,372/155,100/64,420/24,764 triangles across the four Scots-pine levels and 1,280/320/80/20 across the boulder levels. The ZIP artifacts were 65.7 MB for pine and 34.7 MB for boulders; the GLBs repeat embedded material images, so geometry reduction does not translate into equivalent download-size reduction. The runtime embedded-image cache hashes encoded bytes, and identical LOD materials now share one scene material index. Repeated generation also produced byte-identical pine and boulder ZIP/GLB hashes between runs 42882137917 and 42889486320, confirming deterministic Blender outputs. The Scots-pine generator emits deterministic, closed shallow-volume snow caps on the upper surfaces of near-horizontal primary and secondary boughs. Each cap has a seven-point rounded cross-section, a tapered five-station length profile, a buried underside and end faces, for 66 triangles per cap. The fixed seed emits 120 / 80 / 42 / 18 caps across LOD0–LOD3. The source generator checks manifold edge incidence, non-degenerate faces, and non-degenerate fan-triangulated UV bases before export. Snow end faces use a two-axis planar projection of the rounded cross-section; a constant-U end-cap projection previously produced 1,200 zero-area UV triangles in LOD0. The Blender verifier re-imports each GLB, welds duplicated seam vertices by position, requires exactly two incident faces per snow edge, and validates every imported triangle's UV determinant against the engine validator's 1.0e-8 tangent-space threshold. The manifest records cap and triangle counts per LOD, and the verifier checks exact manifest/import agreement, LOD-specific snow-density floors and ceilings, and baseline bark/needle triangle floors. CI renders seven PBR review angles, including a dedicated upper-crown snow detail, and archives the PNGs and contact sheet alongside the runtime model. These snow caps remain an art-directed geometry approximation, not a physical snow-transport simulation. Culling diagnostics report visible instances by LOD and estimated submitted triangles versus the full-detail baseline. The Scots-pine LOD3 hint (0.035) is not reached within the current 280 m vegetation draw cap using the measured LOD0 bounding radius (~17 m); the boulder LOD3 is reachable within its 720 m cap. Aggregate capture counts do not yet separate pine and boulder selections, so pine LOD3 calibration remains open. These are CPU-side scene-submission counts, not GPU timestamps or proof of a frame-rate gain. The D3D12 capture job in run 42884472600 produced seven Sakkola and seven Taipale views; renderer logs report 3,978 Sakkola placements/12,023 material-bound instances/104 meshes/87 materials and 698 Taipale placements/2,008 instances/82 meshes/65 materials. The CI workflow writes per-view camera, LOD-selection and non-empty triangle-budget diagnostics into `renderer.log` and requires those diagnostics for both scenes. The successful full validation [run 42892103260](https://github.com/ItsDropper/Talvisota/actions/runs/42892103260) recorded seven views per scene with zero invalid LOD selections. Sakkola's estimated visible-set triangle reductions were 54.75% (overview), 61.67% (church village), 54.38% (forest), 53.15% (farmstead), and 59.48% (church interior); the shoreline and farmhouse-interior views had no visible LOD-enabled instances. Taipale's forest and command-hut views reduced estimated submissions by 52.50% and 56.33%; its other five views reduced by only 0-0.69%. These are CPU-side index-count estimates, not GPU timings. ### Wind-coupled snow displacement

The parent world's validated `wind_direction` and `wind_strength` are copied into the loaded `WorldRegion` so CPU terrain sampling and renderer mesh refinement consume the same inputs as the environment presentation. `snow_drift_v1` keeps broad moraine relief and fine granular variation independent of wind, but rotates its anisotropic ridge and drift fields into along-wind/cross-wind coordinates. A bounded lee-side term adds accumulation on terrain slopes descending in the authored wind direction, using the bilinear heightfield gradient. The wind response is calibrated at 0.06 strength, doubles at 0.12, and saturates above that value to keep the displaced surface bounded. Frozen-water surfaces remain undisplaced.

The deterministic displacement is shared by terrain mesh refinement, `SampleTerrainHeight`, placement grounding, and traversal. `Talvisota.World.Region` tests cover wind-direction changes, zero-wind invariance, lee-slope accumulation, deterministic repeat sampling, parent-world wind propagation, non-finite coordinates, and water exclusion. This is an art-directed wind-coupled surface response, not a snow-transport simulation or a replacement for higher-resolution georeferenced elevation data.

### Frozen river surface texture density

The Taipale frozen-river ribbon uses a 64-metre physical repeat for the shared ice PBR maps. UV U is derived from cumulative distance along the curved river centreline, while V is derived from each cross-section's bank-to-bank width. The previous 8-by-1 UV range stretched the 1024px ice maps over roughly 585 metres along the river and 120 metres across it, making the fracture and granular pattern far too large. The environment asset contract test checks all 65 cross-sections against their world-space distances and verifies the OBJ face-to-UV indices. The Sakkola frozen-water mesh retains its separately authored 64-metre repeat.

The frozen-ice material is a dielectric: its base-colour factor is white, metallic is zero, and Pr=1 leaves the roughness map as the absolute linear roughness field. The previous generated ice roughness map averaged 0.328; multiplying it by the MTL Pr=0.78 produced an effective mean near 0.256, while Pm=0.12 introduced an inappropriate metallic reflection response. The revised deterministic field samples at 0.594 on the generator's 64x64 validation lattice and must remain within 0.56–0.68. talvisota_environment_texture_gen --verify also checks the generated BMP channel mean (140–180/255). The environment asset contract test verifies the dielectric factors and that the albedo, normal and roughness maps remain bound. This is a material calibration, not a photorealism acceptance claim; the next D3D12 capture still requires visual review.

## Typed mission, faction, character, and equipment definitions

The content library parses strict v1 `.tmission`, `.tfaction`, `.tcharacter`, and `.tequipment` records. Their required fields and reference types are documented in [authored-definitions-v1.md](../../data/schemas/authored-definitions-v1.md). The parser validates type/version headers, unique and known fields, required values, manifest identity/path ownership, expected referenced asset kinds, referenced file presence, and explicit manifest dependencies. Failed parsing leaves the caller's previous output unchanged. Generic JSON/TOML/YAML definitions fail closed until parsers are implemented.

## Packaging and provenance

On Windows x64/MSVC, `talvisota_content_package <manifest> <content-root> <package-dir>` validates typed definitions and engine-backed media, stages every present manifest asset, writes a normalized `content.tmanifest`, and writes a deterministic `package.tmanifest` containing the catalog digest plus stable ID, kind, relative path, byte count, SHA-256, source, and licence/permission metadata. Before replacing the destination, the staged package is reloaded from its own catalog; dependencies, typed definitions, model/texture/audio decoders, path containment, exact inventory coverage, byte counts, and hashes are revalidated. `talvisota_content_package --verify <package-dir>` performs the same full semantic and integrity verification. The inventory is not a cryptographic signature or proof of asset ownership.

Every manifest record requires source and licence/permission metadata. Keep source media immutable; write processed outputs into a separate build directory. A clean content build must validate all shipped definitions and references before packaging. External asset rights must be documented before an asset is committed. Optional manifest assets may be absent; when present, they are validated with the same strict rules as required assets. Engine-backed audio validation fully decodes bounded RIFF/WAVE PCM (8/16/24/32-bit), IEEE-float32, Ogg Vorbis, and FLAC streams. WAV chunk bounds, sample rate/channel/alignment limits, complete frames, and finite samples are checked. OGG and FLAC use vendored stb_vorbis and dr_flac decoders, run in bounded PCM chunks, and enforce encoded-size, duration, channel-count, and sample-rate limits.


## Renderer capture diagnostics

The Windows MSVC renderer-adapter CI job renders five genuine D3D12 Sakkola viewpoints for 30 frames each. Its `renderer.log` artifact records the submitted scene placement/draw/unique-mesh/material counts and per-view average/p95 wall-frame time plus average/p95 `Render()` CPU-call time. Wall-frame timing includes the sample's 16 ms pacing delay; `Render()` timing is CPU-observed call duration and may include driver/present blocking. Neither value is a GPU timestamp measurement. CI runner numbers are useful for regressions on the same runner class only; they do not establish target-PC performance or replace real-device D3D11/D3D12 profiling and visual review.


Screenshot CI uses one rendered frame per viewpoint and disables the sample's interactive 16 ms frame pacing while capture mode is active. This minimizes capture overhead; its single-frame timing is diagnostic only and is not a stable performance benchmark. Interactive renderer mode retains frame pacing.

The capture validator checks a broad set of bright blue-dominant pixels across the upper quarter of each presented BGRA frame instead of assuming one fixed coordinate is unobstructed sky. This tolerates legitimate roof/tree occlusion while still rejecting a missing sky region or swapped framebuffer colour channels. It is a readback-integrity diagnostic, not a visual-quality acceptance test.
